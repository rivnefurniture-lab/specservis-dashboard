# Спецсервіс — управлінський дашборд

Внутрішній дашборд для контролю тендерної воронки, реалізації проєктів, покриття ринку та конкурентів. Застосунок побудований на Next.js 16 (App Router), працює на Vercel і читає робочі джерела без змін. Опціональний експорт у виділену Excel-книгу та email-сповіщення працюють через окремий мінімально привілейований Entra-контур.

> **Репозиторій має залишатися приватним.** Bundled snapshot-файли містять внутрішні робочі статуси, примітки та відповідальних. Не підключайте до нього публічний remote і не публікуйте build-артефакти.

## Архітектура і джерела даних

```text
SharePoint / Microsoft Graph (read-only) ─┐
                                          ├─ Next.js API ─ браузер користувача
SmartTender / Prozorro (read-only) ───────┤
Official Prozorro + Contracting API ──────┤
Neon PostgreSQL (analytics v2) ───────────┤
                                          │
Vercel Blob (актуальний зріз ринку) ──────┘
                ↑
       незалежні Vercel Cron за власним розкладом

src/data/*.json ─ резервні перевірені зрізи для роботи при відмові джерела
```

- `src/app/api/dashboard` — внутрішній реєстр і покриття ринку.
- `src/app/api/projects` — воронка та реалізація проєктів.
- `src/app/api/competitors` — аналітика з локального зрізу конкурентів.
- `src/app/api/analytics-v2` — фільтри, KPI, учасники, договори й матриця «постачальник × замовник».
- `src/app/api/tender-workspace` — захищена робоча черга тендерів кондиціонування: читання, синхронізація та версійне редагування людських рішень.
- `db/analytics-v2.sql` — нормалізовані закупівлі, лоти, пропозиції, рішення, договори, зміни, платежі й пресети.
- `src/app/api/cron/market` — часткове планове оновлення ринку кожні три години.
- `src/app/api/cron/analytics` — discovery та офіційні change-feed кожні 5 хвилин; `src/app/api/cron/analytics-import` незалежно обробляє durable queue, тому довга історія не затримує нові тендери.
- `src/app/api/cron/tender-notifications` — надсилання відфільтрованих нових/змінених закупівель кожні 15 хвилин із захистом від повторів.
- `src/app/api/cron/spending` — окреме погодинне підтвердження оплат через Spending.gov.ua.
- `src/app/api/confidential/turnover` — фінансові факти для вбудованого режиму власника: оборот, FTE, продуктивність, ФОП, концентрація та управлінські сигнали. Endpoint вимагає основну сесію саме акаунта з `financeAccess`; звичайний owner цього права не має.
- `db/confidential-turnover.sql` — версійне серверне сховище нормалізованих місячних фактів. Первинний Excel не входить у репозиторій, frontend bundle або deployment.
- `src/data/*.json` — згенеровані резервні дані. Не редагуйте їх вручну.

Основна Microsoft Entra application повинна мати лише `Sites.Selected` для читання конкретного робочого сайту. Якщо ввімкнено email/Excel-експорт, використовуйте іншу application з `Mail.Send` і `Sites.Selected` Write лише на виділений сайт експорту. Облікові дані та персональні дані не можна додавати до Git або вставляти в документацію.

## Локальний запуск

Потрібні Node.js 24 та npm 10 або новіший. Версію Node зафіксовано у `.nvmrc`.

```bash
nvm use
npm ci
cp .env.example .env.local
npm run dev
```

Відкрийте [http://localhost:3000](http://localhost:3000). Для UI на резервних snapshot-файлах зовнішні ключі не потрібні. Для live SharePoint, оновлення ринку та Blob заповніть відповідні змінні у `.env.local`.

Перед кожною зміною виконуйте повну перевірку:

```bash
npm run verify
```

Окремі команди: `npm run typecheck`, `npm run lint`, `npm test`, `npm run build`.

## Змінні середовища

Повний безпечний шаблон міститься у `.env.example`. У production обов'язкові:

- `SESSION_SECRET` — окремий випадковий секрет підпису сесій;
- `DASHBOARD_ACCOUNT_CREDENTIALS` — sensitive JSON із scrypt-verifier стандартних акаунтів; значення не зберігається в коді;
- `CRON_SECRET` — секрет Vercel Cron без кінцевого переносу рядка;
- `SMARTTENDER_USERNAME`, `SMARTTENDER_PASSWORD` — read-only доступ до пошуку;
- `MICROSOFT_TENANT_ID`, `MICROSOFT_CLIENT_ID`, `MICROSOFT_CLIENT_SECRET` — Entra application із мінімальним Graph-доступом;
- `BLOB_READ_WRITE_TOKEN` — Vercel Blob для актуального ринкового зрізу.
- `DATABASE_URL` — PostgreSQL/Neon для повної аналітики й спільних серверних пресетів.
- `CONFIDENTIAL_USERNAME`, `CONFIDENTIAL_PASSWORD_SALT`, `CONFIDENTIAL_PASSWORD_HASH` — реквізити `executive.vault`, який отримує звичайну основну сесію з окремим правом `financeAccess`; `CONFIDENTIAL_SESSION_SECRET` тимчасово підтримує перевірку старих коротких сесій під час міграції;
- `CONFIDENTIAL_IMPORT_SECRET` — окремий Bearer-секрет для версійного імпорту місячних фактів.

Вихідні інтеграції налаштовуються лише за потреби: `TENDER_INTEGRATION_*` — окрема Entra application; `TENDER_NOTIFICATION_SENDER` — дозволена службова скринька; підписки з одержувачами керівник зберігає у вебінтерфейсі; `TENDER_EXCEL_SITE_ID`, `TENDER_EXCEL_DRIVE_ID`, `TENDER_EXCEL_ITEM_ID` — виділена книга експорту. Без цих змінних тендерний модуль працює повністю, але чесно показує email та Excel як неактивовані.

Згенеруйте незалежні секрети командою `openssl rand -base64 48`. Ніколи не копіюйте значення між `SESSION_SECRET` і `CRON_SECRET`. Файл `.env.local` уже виключений із Git; локально обмежте його права командою `chmod 600 .env.local`.

## Побудова резервних зрізів

Побудова перезаписує відповідний файл у `src/data`, тому спочатку перевірте джерело та дату, а після побудови перегляньте diff і запустіть `npm run verify`.

```bash
# Внутрішній тендерний реєстр із локальної книги; напрямок типовий — Капбудівництво
npm run snapshot:internal -- /absolute/path/закупівлі.xlsx Капбудівництво

# Ринок зі SmartTender/Prozorro
npm run snapshot:market

# Історична аналітика конкурентів
npm run snapshot:competitors

# Проєкти: із Graph без аргументів або з двох локальних книг
npm run snapshot:projects
npm run snapshot:projects -- /absolute/path/pipeline.xlsx /absolute/path/delivery.xlsx
```

Для точного часу джерела використовуйте `INTERNAL_EXPORTED_AT` або `PROJECTS_EXPORTED_AT`, а не час локального копіювання файлу. Збірки ринку й конкурентів виконують багато зовнішніх запитів і можуть тривати довго.

## Аналітика v2

Без `DATABASE_URL` розділ «Аналітика» лишається доступним на чесно позначеному legacy-зрізі. У ньому немає дат рішень, прямих договорів, змін та оплат, тому UI показує ці поля як відсутні, а не як нуль. Для повного режиму спочатку застосуйте схему:

```bash
npm run analytics:migrate
```

Імпорт приймає JSON-масив записів `{ "tender": <official tender detail>, "contracting": <optional Contracting API response>, "direction": <optional department> }` або об'єкт із `records`, `scope`, `datasetId`, `sourceName` і `filters`:

```bash
npm run analytics:import -- /absolute/path/prozorro-bundle.json
```

Для окремого розширеного набору оберіть `scope=expanded` і задайте ДК-код або предметний термін. API створить відтворюваний dataset для точного набору «період + ДК + термін», а планувальник дозаповнить його по одному дню за запуск. Готові активні розширені набори освіжають останні два дні не рідше ніж раз на шість годин. Моніторинговий та розширений набори можуть посилатися на ті самі канонічні закупівлі без дублювання фактів.

Автосинхронізація має незалежні курсори й lease-блокування для discovery, офіційних tender/contract change-feed та імпорт-черги. Курсор зсувається лише після гарантованого запису ID у PostgreSQL. Discovery працює кожні 5 хвилин, імпорт-черга — щохвилини: нові закупівлі не чекають завершення історичного batch. Типовий імпорт — 100 записів із повторними спробами та exponential backoff; помилкові записи залишаються у durable queue. Для будівництва/сервісу застосовується Київ/Київщина політика моніторингу, для кондиціонування — вся Україна. Готовий dataset доступний під час backfill, а прогрес і залишок черги показані у UI.

Погодинний spending cron перевіряє договори незалежно від discovery. У підсумок оплат потрапляють лише збіги з підтвердженою парою ЄДРПОУ та структурованим ідентифікатором закупівлі; ймовірні збіги зберігаються тільки для аудиту. Автоматичний change-feed завжди оновлює офіційне `amountPaid` із Contracting API.

Три часові лінзи навмисно незалежні: участі — дата публікації, перемоги — дата рішення, договори — дата підписання. Прямий договір без оприлюдненої пропозиції враховується у договорах, але не в участях. Суми ніколи не змішуються між валютами, а відсутнє значення не прирівнюється до нуля.

## Робоча черга кондиціонування

Операційний модуль перетворює реєстр із Excel на спільний веб-процес. Кожен цикл analytics cron додає нові релевантні закупівлі кондиціонування з канонічної бази, оновлює факти Prozorro і не перезаписує рішення працівників. У відкритому браузері черга додатково перечитується кожні п'ять хвилин. Тому ранкові закупівлі потрапляють у роботу автоматично, а ручне оновлення керівника потрібне лише для контрольної перевірки.

Початкові факти — номер, замовник, ЄДРПОУ, регіон, предмет, процедура, ДК, строки, адреса поставки, вартість, гарантія, кількість, умови оплати, пропозиції, переможець і договір — беруться з нормалізованих даних Prozorro. Працівники ведуть лише робочий шар: рішення про участь, етап, відповідального, наступну дію, причини та примітки. Керівник додатково керує призначенням, пріоритетом і управлінською приміткою. Кожна зміна має версію та запис у журналі подій, тому паралельне редагування не губить чужу роботу.

Доступ надається окремим capability `tenderWorkspaceAccess` лише керівнику та працівникам напряму кондиціонування. Звичайний owner, `executive.vault` та інші відділи не бачать пункт меню, а прямий запит до API отримує `403`. Таблиці `tender_work_items` і `tender_work_events` не прив'язані до Excel-розкладки, тому той самий контрольований процес можна згодом увімкнути для інших відділів і консолідувати на рівні компанії без дублювання закупівель.

## Фінансовий режим executive.vault

Фінанси не є окремою сторінкою: `executive.vault` входить в основний кабінет і бачить верхній перемикач «Тендери / Фінанси». У фінансовому режимі бокове меню перемикається на фінансові розділи. Для стандартних owner/manager/employee верхній перемикач, фінансове меню та сам компонент взагалі не рендеряться. Це не лише UI-обмеження: `/api/confidential/turnover` перевіряє `financeAccess` серверно й повертає `403` навіть звичайному owner. Старий URL `/confidential` лише переводить дозволену основну сесію в `/?workspace=finance`.

Фінансові записи зберігаються лише в окремій схемі Neon і не входять до Git-репозиторію чи bundled snapshot. Водночас репозиторій містить резервні зрізи тендерного та проєктного контурів, тому навіть read-only доступ до GitHub надавайте лише довіреним розробникам. Доступ `write` або `admin` не слід видавати для звичайного перегляду коду.

Основна cookie має `HttpOnly`, `Secure` у production та `SameSite=Lax`. Фінансові відповіді не кешуються й містять `X-Robots-Tag`.

Імпорт приймає лише нормалізований JSON через захищений Bearer endpoint. Нове джерело спочатку записується як окрема версія; активний pointer перемикається лише після звірки кількості місяців. Сирий Excel не слід копіювати у `src`, `public`, Blob із публічним доступом або deployment logs. Після оновлення книги повторіть локальний контроль типів/формул, сформуйте нормалізований payload і запустіть захищений імпорт.

## Розгортання

1. У Vercel виберіть Node.js 24 і додайте production-змінні з `.env.example`.
2. Підключіть Blob store та переконайтеся, що `BLOB_READ_WRITE_TOKEN` створено платформою.
3. Підключіть Neon/PostgreSQL. Локально можна застосувати `npm run analytics:migrate`; у Vercel захищений cron і ручний refresh ідемпотентно застосовують ту саму схему перед першим sync, бо sensitive managed credentials доступні лише всередині Function.
4. Перевірте Entra-дозвіл `Sites.Selected` саме для потрібного SharePoint site.
5. Локально виконайте `npm ci && npm run verify`.
6. Розгорніть: `npx vercel --prod`.
7. Перевірте вхід, усі дозволені для ролі розділи, свіжість джерел і відповідь cron endpoint із коректною авторизацією.

Після зміни `SESSION_SECRET` усі активні сесії стають недійсними. Після ротації Graph, SmartTender або Blob credential спочатку оновіть Vercel, перевірте production, і лише тоді відкликайте попередній credential.

## Відновлення і реагування

Якщо SharePoint недоступний, застосунок має показати останній перевірений `internal-snapshot.json` або `projects-snapshot.json` із позначкою про резервне джерело. Не маскуйте цю позначку. Після відновлення Graph перевірте, що live-файл новіший за bundled snapshot і кількість записів не зменшилася неочікувано.

Якщо Blob або оновлення ринку недоступні, читання переходить на `src/data/market-snapshot.json`. Відновіть Blob credential, запустіть одне контрольоване оновлення й звірте `generatedAt`, кількість записів та помилки обходу. Не запускайте кілька повних збірок одночасно.

При підозрі на витік секрету:

1. Негайно ротувати скомпрометований credential у системі-власнику.
2. Оновити його у Vercel та локальних захищених середовищах.
3. Для `SESSION_SECRET` завершити всі сесії ротацією; для Entra перевірити audit log; для Blob перевірити операції зі сховищем.
4. Перевірити Git history і deployment logs на наявність значення. Не публікувати сам секрет у задачі чи звіті.

Детальні вже відомі симптоми та виправлення зібрано у `TROUBLESHOOTING.md`.

## Контрольний список експлуатації

- Щодня: перевірити час останнього SharePoint sync, market snapshot і синхронізації робочої черги, а також повідомлення про fallback/error.
- Щотижня: переглянути невдалі оновлення, кількість записів та аномальні зміни покриття.
- Після імпорту аналітики: звірити coverage/warnings, один лот із кількома учасниками, один прямий договір і одну зміну договору з Prozorro.
- Щомісяця: перевірити список користувачів, ролі, Entra grants і доступ до Vercel.
- Після зміни схеми Excel: перебудувати snapshot, прогнати тести словників/зіставлення та звірити підсумки з книгою.
- Перед релізом: `npm run verify`, перегляд diff згенерованих JSON і smoke test production.

## Межі безпеки

HTTP-відповіді отримують CSP, заборону iframe, MIME sniffing, доступу до камери/геолокації/мікрофона та HSTS у production. Поточна статична CSP мусить дозволяти inline bootstrap Next.js; для повної відмови від `unsafe-inline` потрібні nonce, які генеруються на кожен запит.

Це внутрішня система, а не архів первинних документів. Резервні snapshot-файли забезпечують доступність, але не замінюють резервування оригінальних книг SharePoint і журналів доступу.
